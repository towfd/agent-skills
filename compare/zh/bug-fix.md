### 修 bug

**這件任務是你的責任。規劃、審查、驗證。** 把調查和修正交給 subagent，你自己保持帶頭。依工作挑每個 subagent 的推理等級，照 Subagents 那一節。

要科學。每一行出貨的程式都要追得到執行期的證據。「可能有幫助」的雙重保險是一個假設，不是修正。它不出貨。當證據推翻一個假設時，把因它而做的改動退回。只出貨證據撐得起的最小改動，多的都不要。

1. 透過操控 skill（不能妥協的事）在對應的介面上自己重現它，即使某個除錯或量測流程說要請使用者重現也一樣。只有在你講得出一個具體的理由、說明操控介面碰不到目標，而且已經把它操作到極限之後，才去問使用者。如果沒辦法直接重現，就合成觸發條件、收緊條件，或加量測程式碼，直到它發生為止。
2. 用二分法找原因。先列出候選的假設，再一個個排除，直到剩下一個。用受影響子系統的一份追蹤紀錄，加上查回歸歷史的 **why** skill，當作這些假設的起點。每一輪都挑能砍掉最多剩餘問題範圍的切法，拿到執行期證據，排除。程式狀態不清楚時，加量測程式碼或 log，在程式執行時讀它。不要猜。很長或很頑固的追查，用 Cursor 的 `/loop` 指令來推動。在第 3 步的 `architect` 或分頭派出 `interrogate` 之前，先用執行期證據確認那個存活下來的*機制*。
3. 規劃修正。如果它跨過函式邊界，先 `architect`。把實作交給一個 subagent，用你設定的 bug-fix 模型（預設 `claude-opus-5-5-xhigh-fast`），並給它具體的範圍。
4. 在同一個介面上驗證。原本的重現現在通過。「無法判定」或驗錯介面都不算通過。把它標出來。單元測試只顯示分支的行為，不代表沒有 bug。
5. 把 commit 排好，讓失敗的重現在 git 歷史裡比修正先落地。當這個 bug 有便宜的本機測試路徑時，看 **tdd** skill 的「先寫失敗的測試」節奏。如果測試會很昂貴、很吃整合，或不清楚怎麼測，就跳過。
   這就是 **sequence-verifiable-units** 原則 skill 的標準範例，失敗的測試在先，修正疊在上面。
6. 執行 **Opening a PR**。

**回覆：** 壞掉的是什麼、根本原因、修正、你怎麼驗證的。把先失敗後通過的重現輸出原封不動貼上。
