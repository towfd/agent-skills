# 共用狀態先分開，再談排隊

當同時運作的角色可能寫到同一個檔、分支、鍵或物件時，先問它們需要的是一個共用的物件，還是其實在發布各自獨立的事實。預設給每個角色它自己的檔、鍵、分支或狀態目錄，只在讀取狀態的地方合併。兩個工人各自把自己的欄位寫進同一個 `state.json`，仍然是共用的修改。

只有當「一個共用的寫入目標」真的是一條不變條件時，才用結構的方式讓存取排隊（鎖檔、單一寫入者、依序進行的階段、比較後交換（compare-and-swap））。指示不是並行控制，而「我們需要一把鎖」是一個該先檢查的警訊。
