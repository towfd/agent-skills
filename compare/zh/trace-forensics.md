TOPIC: 分析現成的追蹤檔

### 追蹤紀錄鑑識

**從擷取檔得出診斷是你的責任。**

這跟 **Runtime forensics**（執行期鑑識）不一樣，那份是對執行中的程序做量測。這裡擷取的東西已經存在。擷取檔是固定的資料集，讀它，不要重跑。工具保持通用：cpuprofile 和 `.json.gz` 用 DevTools 或追蹤紀錄解析器，spindump 用文字編輯器，heapsnapshot 用你的 heap 工具。

1. 認出格式，用對的工具載入。大的擷取檔交給 subagent 解析（**principle-guard-the-context-window** skill），主對話只留縮減後的發現。依工作挑每個 subagent 的推理等級，照 Subagents 那一節。
2. 把原始的擷取檔轉成你能查詢的形式。把追蹤紀錄或 heap 快照倒進 sqlite，每個取樣、堆疊框或節點一列。先轉成能查詢的形狀，再開始讀。
3. 縮小到原因。查出佔用最多時間的堆疊框，沿著呼叫樹走到熱路徑。如果是記憶體洩漏，沿著持有鏈從洩漏的物件走到 GC root。如果是 spindump，找出卡在 CPU 上或被擋住的執行緒，以及它在等什麼。
4. 歸到原始碼。用擷取檔自己帶的符號，把熱點堆疊框對到檔案、符號和行數。沒有對應到原始碼的堆疊框，還不算診斷。把符號解析出來，或直接講明這份擷取檔沒有帶符號。
5. 如果你有成對的擷取，比對前後兩份擷取檔來確認。否則，把發現標成這份擷取檔所支持的最強假設，而不是已確認的原因。
6. 交回附出處的診斷，沒被要求就不修。原因一確定，就導到 Bug fix（修 bug）或 Perf issue（效能問題）。吞吐量檢查點只寫一行：`throughput checkpoint: n/a, read-only forensics`。

**回覆：** 擷取檔和它的格式、縮減後的發現、原始碼位置、擷取檔的路徑，以及有沒有成對的擷取確認過。
