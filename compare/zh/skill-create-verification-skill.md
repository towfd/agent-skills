# 建立一個驗證 skill

每個認真的專案，都需要一個用腳本操作真正的 app、證明行為的方法：啟動它、照使用者的方式操作一個功能，並擷取證據。這個 skill 把它產生成一個放在專案裡的 skill（`.cursor/skills/verify-<app>/`），依這個倉庫量身打造。你產生出來的東西是寫給下一個 agent 看的，不是給人看的：讀它的會是一個從沒看過這個 app 的 agent，在任務做到一半時、沒有任何前情地讀它。

## 1. 訪問倉庫，不是訪問使用者

從程式碼回答下面這些，只問使用者你觀察不到的東西：

- **Surface（介面）：** 使用者實際碰到的是什麼？網頁 UI、CLI／TUI、桌面 app、API、手機 app、函式庫？一個倉庫可能有好幾個；挑主要的那個，其餘的記下來。
- **Run（執行）：** app 在本機怎麼啟動？優先用倉庫自己文件裡寫的開發指令（package 的 scripts、Makefile、README 的快速上手）。記下連接埠、環境變數、種子資料、認證。
- **Drive（操作）：** agent 要怎麼用程式跟它互動？先找現有的驗證工具：Playwright／Cypress 的 spec、expect 腳本、PTY 輔助工具、可以用 curl 打的端點、除錯連接埠。找不到才挑通用的做法：網頁和 Electron 用瀏覽器／CDP，CLI／TUI 用 tmux／PTY 驗證工具，服務用單純的 HTTP。
- **Observe（觀察）：** 能擷取到什麼證據？截圖、終端機對話紀錄、回應內容、log、結束碼、資料庫狀態。
- **Isolate（隔離）：** 兩個實例能不能同時並排跑（連接埠、資料目錄、profile）？不能的話，就在產生的 skill 裡寫明：拒絕兩邊同時操作一個共用的實例，總比弄壞使用者的工作階段好。

如果簽出的程式照原樣沒辦法建置或啟動，就在產生之前先修好（或精確地回報）；對著一個壞掉的基礎寫出來的 skill，會教錯步驟。當一個不相干的缺少檔案擋住啟動（一個 API 從不提供的靜態目錄、一份範例設定檔），產生的 skill 可以建立它，清楚標示是驗證用的臨時鷹架，並在清理時移除。

## 2. 產生 skill

寫 `.cursor/skills/verify-<app>/SKILL.md`，要有 YAML 檔頭（`name: verify-<app>`，以及一個寫出 app、介面和什麼時候該用它的 `description`；沒有檔頭，這個 skill 永遠不會被登記），還有下面這些段落，每一段都要以訪問實際找到的東西為根據（不留任何佔位符）：

- **Launch（啟動）：** 為了驗證而啟動 app 的確切指令，以及怎麼判斷它已經就緒（一行 log、一個提示字元）。Launch 必須能從空的資料目錄一路到可以用的狀態，包括所有的 migration 和種子資料。就緒的意思是可以用，不只是有個程序會回應。資料庫的健康檢查可能已經通過，它的初始化腳本卻還在跑。要包含關閉的方法。如果是很快就結束的 CLI 或 TUI，沒有伺服器需要一直開著：啟動的意思是先建置一次執行檔（或安裝相依套件），然後每次操作都在它自己隔離的 PTY 或 tmux 工作階段裡開始。
- **Doctor（健檢）：** 一個唯讀的檢查，回答「這個實例值得操作嗎？」：程序有在跑、版本／build 對、連接埠是我們佔的、認證有效。只要有任何東西看起來不對，agent 就先跑這個。
- **Drive（操作）：** 驗證工具的操作步驟，用這個倉庫裡真實的選擇器／指令，不是範例。優先用穩定的把手（ARIA 標籤、data 屬性、提示字串、路由路徑），不要用座標和 tab 順序。
- **Evidence（證據）：** 為了證明要擷取什麼、放到哪裡。寫明證明的標準：走真正的使用者路徑，不是內部的 setter 或只給測試用的端點；擷取動作和它造成的狀態，不是只有最後的畫面；除了看得到的東西，也要驗證副作用（寫入的檔案、新增的資料列、送出的訊息）；只有在正式環境的邊界本來就把外部系統隔開的地方，才用 mock。當安全的路徑是 dry-run 或測試模式時，要靠觀察（檔案、網路、git ref）去驗證它實際跳過了什麼，不要相信它的名字：有些 dry-run 還是會連網路或打開瀏覽器。
- **Cleanup（清理）：** 怎麼關掉這次執行建立的實例。絕不要用程序名稱去砍；砍你自己啟動的。清理會移除實例和暫存狀態，絕不移除證據：證明用的成品在關閉之後還要留著，放在 skill 指定的位置。
- **Helpers（輔助工具）：** skill 附帶的任何腳本都要可以執行，而且 skill 內文裡要寫出怎麼呼叫它。讀的人還得自己逆向推敲的輔助工具，就不算輔助工具。

## 3. 建立功能地圖的初版

建立 `.cursor/skills/verify-<app>/features/README.md`，再加上你認得出來的每個面向使用者的功能各一個檔（一開始先瞄準最重要的 3 到 5 個，從路由、指令、選單或文件找）。照 [`references/feature-map-example/`](references/feature-map-example/) 的形狀，一個 README 索引，每個功能一個檔。每個檔都從使用者的角度回答：這個功能是什麼、怎麼到得了它、怎麼用驗證工具操作它，以及什麼看得到的最終狀態能證明它可以用。四個 H2 是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果種子資料缺少某段使用流程需要的前提條件，那段流程就回報失敗，原因寫進那個功能的 `Gotchas`。絕不要為了讓它通過而把流程改弱。這份地圖是這個倉庫持續維護的驗證依據；地圖上列了其他入口時，只操作一個方便的入口的證明是不完整的。

## 4. 交出去之前，先證明產生的 skill 可以用

照它自己的指示從頭到尾跑一次：啟動、健檢、操作地圖上的「一個」功能（一個就夠了；地圖存在，就是為了讓之後的執行去涵蓋其他的）、擷取證據、清理。清理之後，確認證據還在指定的位置；把證明吃掉的清理，就是這一步沒過。失敗的地方要修，而且每一輪失敗之後也要跑產生出來的清理，免得失敗的嘗試留下沒人管的程序和連接埠。一個從沒被執行過的 skill 是草稿，不是能交出去的東西。如果你是在真正目標的替代品上證明它的（用容器代替全新的 VM、用本機的環境代替遠端的），就列出替代品做了、但真正目標不會做的每一個設定步驟。這些步驟在真正目標上有一次執行涵蓋到之前，都還算沒驗證。

## 5. 提供維護的循環

告訴使用者可以用 `/maintain-verification-skill`，在 app 改變時讓地圖保持真實。只有在使用者問的時候，才建議多久做一次。
