# 自己想辦法

當任務對不上任何劇本時，就設計一份。寫任何程式之前要交出的，是工作流程本身：一連串的階段，依任務調整嚴謹程度、照科學方法進行，並留下一份人離開後回來可以稽核的決策軌跡。

## 開始

開一個待辦清單，第一項是讀 **poteto-mode** skill 的 Principles 那一節。然後把下面的階段加成待辦項目。

## 階段 A：界定框架

先掌握實際狀況，再投入。在你能講出下面這些之前，不要開始執行：

- 用一個可以被證偽的判斷條件來定義完成（**prove-it-works** 原則 skill）。
- 量化過的範圍：大概有多少單元和工作量，加上掌握狀況時發現的阻礙。
- 嚴謹程度，寧可偏高。一做就回不了頭的單向門和波及範圍大的，要更嚴謹。可以退回、風險低的步驟，可以少一點。嚴謹指的是關卡和成品，不是「更努力」。

在投入一次很長的執行之前，先把框架和取捨提出來。可以退回的工作就直接進行（**never-block-on-the-human** 原則 skill），但要跑好幾個小時的執行，值得設一個檢查點。

## 階段 B：設計工作流程

拆成不可再分、能各自獨立落地的單元。風險最大的未知先做。骨架和驗證排在功能之前（**foundational-thinking** 原則 skill）。

- 在動工之前先做好驗證工具，基準取自改動之前的狀態，讓檢查讀起來是「舊值 vs 新值」。
- 遇到單向門的設計決定，跑 **architect** skill（它會跑 **arena**）。形狀已經很具體的機械性工作就跳過。對一個已經定案的設計再跑第二次 arena，是過度設計（**laziness-protocol** 原則 skill）。
- 決定哪些要分頭派出去。只沿著接縫平行處理，並給每個工作者自己的 worktree 或分支（**separate-before-serializing-shared-state** 原則 skill）。不要分得太多。依工作挑每個 subagent 的推理等級，照 **poteto-mode** skill 的 Subagents 那一節。
- 把設計好的階段清單寫下來。那份清單就是人要審查的東西。

然後執行這個設計。把它的步驟當成具體的項目，加進待辦清單裡階段 C 和階段 D 那兩項之間。每一步都照階段 C 的迴圈紀律跑，並把階段 D 的紀錄穿插在其中，每落地一步就記一列，而不是把整份軌跡留到最後才寫。

## 階段 C：跑迴圈

每個單元都是一個實驗。講出假設，做最小的改動，在真正的成品上拿判斷條件來量，有推進就留下，沒有就退回。套用 **sequence-verifiable-units** 原則 skill，每個單元驗證完再開始下一個，不要把檢查堆到最後一起做。

- 檢查成品來驗證，絕不靠自我回報。當某件事太輕鬆就通過時，先懷疑觀察的方法，再懷疑系統。
- 委派出去的工作要配一個評審。如果工作者鑽關卡的漏洞，就重來並把約定收緊。如果關卡本身錯了，就在它自己的改動裡修關卡，不要繞過它。
- 判定只有 VERIFIED（已驗證）、NOT VERIFIED（未驗證）或 INCONCLUSIVE（無法判定）。無法判定不算通過。不要把負面的結果藏起來。

## 階段 D：留下稽核軌跡

透過 **show-me-your-work** skill 記錄這次執行。figure-it-out 的工作通常夠有野心，值得把軌跡 commit 進去，讓審查者能在 PR 裡讀到。軌跡加上 diff，才是讓人回來時能信任這份工作的東西。

## 階段 E：驗證並交回

在真正的產品上拿階段 A 的判斷條件檢查整體，不要只檢查驗證工具。任何一再出現的修正，都編成一道關卡、一條 lint 規則、一項檢查或一個腳本（**encode-lessons-in-structure** 原則 skill）。

**回覆：** 你設計的劇本、嚴謹程度和原因、決策軌跡的路徑、哪些已經拿判斷條件驗證過、哪些還沒解決。
