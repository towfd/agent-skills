TOPIC: 改結構不改行為

### 重構

**契約是你的責任。結構會變。行為不變。** 這跟加行為的 Feature（功能）、修正行為的 Bug fix（修 bug）都不一樣。

如果整理的過程中發現少了某個功能，或有真的 bug，把它拆出去，先對著釘住的契約把結構上的修改出貨。可以重新設計，但要講明這是重新設計，並導到 Feature（功能）。大型或橫跨多處的結構工作歸 **figure-it-out** skill。這份劇本處理的是範圍集中到中等的修改。

1. 先釘住行為契約。追一遍受影響的子系統，弄清楚契約是什麼，然後在任何結構移動之前，寫一個特徵測試、快照或等價比對工具，把目前的行為記下來。如果這一區沒有測試覆蓋，先寫好釘住行為的檢查，再碰結構。型別檢查和 lint 不算釘住行為的檢查。
2. 照 **principle-model-the-domain**，說出程式缺的是什麼結構。形狀已經清楚、而且只在局部時，平淡無奇的程式就留著。改形狀必須刪掉分支或不合法的狀態，不能加間接層。
3. 說出目標形狀。講明如果今天從頭蓋，模組配置、型別和呼叫圖應該長什麼樣（**principle-foundational-thinking**、**principle-redesign-from-first-principles**）。如果目標跨過函式邊界，搬動之前先跑 **architect** skill 定出形狀。
4. 先減再加。引進新形狀之前，先刪掉沒用的程式、收掉只有一個呼叫者的包裝、拿掉多餘的驗證器、移除孤立的參照（**principle-subtract-before-you-add**）。出貨的是能達到目標形狀的最小修改（**principle-laziness-protocol**）。憑猜想、「可能有幫助」的整理，要退回去。
5. 用保留行為的小步驟搬動，每一步都讓釘住行為的檢查維持綠燈。改 API 的形狀時，在同一波裡遷移每個呼叫者並刪掉舊 API（**principle-migrate-callers-then-delete-legacy-apis**）。不要相容用的墊片，不要新舊兩條路並存。每一次改名都對著實際的檔案抽查。改名會悄悄漏掉字串、文字敘述和反向參照裡的用法。機械式的修改交給 subagent，用你設定的重構模型（預設 `claude-opus-5-5-xhigh-fast`），並給明確的範圍（檔案路徑、要搬動的名稱、要維持的行為）。依工作挑每個 subagent 的推理等級，照 Subagents 那一節。
6. 在真實的成品上證明行為沒變，不是「它編得過」（**principle-prove-it-works**）。比較大的改形狀要跑等價檢查：一支比對新舊輸出差異的腳本、一份錄下來的基準拿新程式重播，或透過相關的 control skill 在對應的介面上跑一次冒煙測試。
7. 確認這次修改值得留下。成功的標準是讀者負擔變輕（**principle-minimize-reader-load**）。如果這份 diff 沒有在任何地方減輕讀者負擔，就退回去。
8. rebase 成幾個有順序的小 commit。先一個做減法的 commit，接著是改形狀，再來是後續的整理。用 **sequence-verifiable-units** 這個原則 skill 來安排它們，讓每一片保留行為的修改在下一片之前都維持綠燈。跑 **Opening a PR**（開 PR）。

**回覆：** 改了哪些結構、你拿來對照的釘住行為的檢查、等價的證明、讀者負擔的變化、哪些出貨了而哪些被退回。沒有新行為。
