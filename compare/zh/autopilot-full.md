TOPIC: 一批 PR 全自動合併

### 全自動駕駛

**判定是你的責任，PR 從來不是。每個 PR 由一個負責人從動手做一路帶到合併，而在你的 swarm 證明了要落地的程式之前，什麼都不合併。這個 swarm 從來沒寫過那份程式。**

一個判定只涵蓋一個 patch，綠燈的 CI 只涵蓋一個 head。第 4 步跑一次完整的 swarm，只有重大修改才再跑一次。`playbooks/shipping.md` 裡的 patch-id 規則可以把某一路的結果沿用下去，而每一個新的 head 都需要它自己的綠燈 CI。

1. **操作者的關卡優先。** 授權只涵蓋佇列裡的項目，所以操作者點名說是他們自己的項目，以及佇列以外的 PR，都停在可合併的狀態。要你講出計畫的要求，不算放行。
2. **每個 PR 派一個負責人，並把它的工作放在接替者找得到的地方。** 整個計畫只決定一次要用哪個程式碼託管平台。預設是 GitHub CLI（`gh`）。如果 `command -v origin` 成功，而且 Origin 解析得到這個儲存庫，所有 PR 操作都用 `origin pr`。不然就留在 `gh`，並把這個備援記下來。絕不要求 Graphite（`gt`）。每個負責人是一個 Cursor 雲端 agent，它動手做、照 `playbooks/opening-a-pr.md` 開它的 PR、在真正的成品上證明這次修改、照 `playbooks/babysit.md` 看顧到綠燈，並在第 4、5 步放行之後合併。在那份劇本說要回報 rebase 的地方，負責人自己 rebase 它自己的分支，並用 `git push --force-with-lease` 發布出去。

   早點開 PR，讓 CI 和機器人跟工作同時跑。程式要等過了去 AI 腔那一輪（`cursor-team-kit` 外掛的 `deslop` skill（`/deslop`））和 `/no-comments` 那一輪才算就緒，這樣完整的 swarm 才是跑在完成的程式上。接著 rebase 到目前的主幹上，並在自我證明之前回報程式就緒的 head，這樣驗證才會跑在這個 patch 要落地的那個基準上。之後每一個 head 都要回報，自我證明、CI 和看顧都做完時，回報可合併。修正的回合留在那個基準上，除非主幹出現衝突、弄壞 CI，或落地了一個已知同時在改同一批檔案的修改，因為每次 rebase 都會讓 CI 重跑。在程式就緒的那次推送之前，以及之後任何需要驗證者的推送之前，都要在已經 commit 的 head 上，針對動到的路徑跑這個儲存庫的檢查。

   假設 VM 會掛掉。開始後不久就推送，並照 **show-me-your-work** skill，在根 agent 的儲存區（路徑在系統提示裡）開一份決策紀錄，之後每完成一個單元就先推送，再開始下一個。誰派出 subagent，誰就在那個儲存區記下它的 id、狀態，以及從同類 subagent 過去的執行得出的卡住時限，這樣上層掛掉時，根 agent 還能去探查它。只強推你自己的分支，而且用釘在你最後推送或接手時那個 SHA 的 `--force-with-lease`，遇到任何不是你做的推送，就停下來向根 agent 回報。
3. **負責人從主幹分出去平行跑，絕不疊在一起，** 這樣每個 PR 都能各自落地。
4. **用 swarm 驗證一次。** 完整的 swarm 只跑一次，在程式就緒的 head 上。只有新的行為、重新設計，或一大段新的 diff，才再跑一次完整的 swarm。一次 rebase、一次合併衝突的解決，或一個小修正，在新的 head 上派一個驗證者就好，只改字句的修改則一個都不用。照 **swarm** skill，在程式就緒的 SHA 上分頭派出互相獨立的驗證者。它們重跑各道關卡，透過對應的操控 skill（例如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或一個指名的驅動工具，在真正的介面上實際證明關鍵的行為，並審查 diff。沒有實機那一路，或在你審查可合併報告附的憑據之前，判定都不算乾淨，因為沒有哪一路會相信它沒查過的說法。

   只為你拿得出來的問題擋下 PR，憑據是在這個 head 上跑失敗的一次執行，或一行被這個 PR 改錯的文件。PR 的基準本來就有的問題，不管基準是主幹還是疊在它下面的那個 PR，都不擋，除非這個 PR 複製了它，或新碰到了它。只有使用者會碰到的 bug、沒過的關卡，或出貨出去的文件寫錯，才擋，其他的都放進後續事項。
5. **負責人只合併你驗證過、而且在它要落地的主幹上測過的東西。** 光是 CI 綠燈，絕不足以授權合併。swarm 的各路一開始跑，合併前的準備就要 rebase 到目前的主幹上、回報新的 head，並等 CI 綠燈。

   就在合併之前，抓一次主幹，問它的修改會不會影響這個 patch，因為主幹每動一次就 rebase 一次，永遠沒完。當要落地的程式從來沒被測過時，就 rebase 並等 CI，例如有衝突、有兩邊都改過的檔案，或有修改動到這個 PR 會跑哪些檢查。兩邊都改過的 lockfile 不需要 rebase，條件是凍結安裝在合併結果上通過，而且這個 PR 改到的套件在那裡解析出來跟在 head 上一樣，因為那次安裝測的就是會落地的那份 lockfile，而安裝失敗就代表 rebase 必須把它修好。當主幹改了這個 patch 的呼叫者，或改了這個 patch 依賴的東西，例如它呼叫的程式或某個依賴的版本，就在合併結果上跑這個 patch 的檢查，通過就合併。其他情況就直接合併。如果主幹會逼出合併準備之後的第三次 rebase，就先停住，回報給根 agent，由它來安排互相撞到的工作的先後。
6. **跑根層。** 任何放寬關卡的東西，例如調高的預算或允許清單裡的一筆，都需要驗證者的證明，再加上你重新給的副署，因為想要綠燈的正是負責人。在涵蓋核准的授權底下，那個副署就是核准，而負責人對它的紀錄要指向你的副署，讓某一路可以去查。被停用或改成軟性失敗的檢查，一律要撤回，因為它對每一種情況都不再把關。絕不要給出或繞過程式碼託管平台強制要求的核准，因為沒有任何副署涵蓋得了它。

   操作者一放行，就設好 `/loop 1h` 來稽核，直到沒有任何交辦出去的工作為止，因為長時間的執行會偏掉，agent 也會無聲無息地卡住。每次觸發都從主幹重讀這份劇本並修正偏差，例如沒回報的 head 或沒記錄的 agent，做法是叫它的負責人把它記下來，因為偏差是紀錄上的缺口，不是卡住。它探查每一個 agent，一路到最末端的各路，並用每個 agent 的副作用來判斷它，因為狀態文字和摘要可能藏住一個卡住的子 agent。agent 出錯、沒辦法開始新的回合，或過了它的卡住時限還沒有任何新東西，就算卡住，到第一次觸發時既沒推送、也沒寫下任何一列紀錄的負責人也一樣。在等你或操作者的，不算卡住，所以回應它。卡住的 agent 立刻換掉，不用等它的停止生效。一次觸發如果替操作者改變了什麼，結尾就照 **ketchup** skill 讓操作者跟上進度，什麼都沒改變的那次就不出聲。
7. **操作者說停，就立刻收手。** 暫停傳到每個負責人那裡，就是一道不准做任何寫入的命令。每個負責人回報自己目前的進度，並保留自己的任務說明，直到操作者解除為止。

**回覆：** 照 **ketchup** skill 讓操作者跟上進度，內容涵蓋每個 PR 的狀態和判定、哪些合併了、副署和理由、還沒解決的操作者關卡、擱置的後續事項，並附上每個 PR 和各份紀錄的連結。
