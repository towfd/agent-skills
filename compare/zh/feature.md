TOPIC: 做新功能

### 功能

**設計由你負責。規劃、審查、驗證。** 實作委派出去。你自己保持主導。

1. 把受影響的子系統追一遍。
2. 用 `architect` 定出形狀。
3. 把吞吐量檢查點寫成四個待辦項目。真的不適用的面向（只有一個檔、沒有分頭派工）也保留它那一項，寫上 `n/a: <reason>`，不要拿掉：
   - **會卡住後面的開頭步驟。** 關卡在分頭派工之前跑。
   - **彼此獨立的工作線。** 互不重疊的檔案、服務或層級就平行做。會寫到同一處的就排隊。
   - **共用的可變狀態。** 預設把目標拆開（**separate-before-serializing-shared-state** 原則 skill）。只有為了真正的不變條件才排隊。
   - **最小的安全拆法。** 如果一個工人最好，講出為什麼。
4. 把寫程式委派給一個 subagent，用你設定的 feature 模型（預設 `claude-opus-5-5-xhigh-fast`），並給它明確的範圍（檔案路徑；點名的資料形狀和它的組織結構，照 **principle-model-the-domain**：用狀態機而不是零散的布林值、用表或登記簿而不是分支、用有型別的模型而不是重複的形狀假設，而且要在被委派的人寫邏輯之前就選好；以及成功標準）。依工作挑每個 subagent 的推理等級，照 Subagents 那一節。當實作有好幾種都說得通的形狀（錯誤處理、抽象層、測試結構），改用 **arena** skill 來委派，讓參賽的人把各種做法擺出來，再由交叉評審替最後的選擇把關。這是強制的：不能用「附上理由跳過」當逃生口，Laziness Protocol（懶惰協定）也不能凌駕它（好處在於審查分開，不在省下幾行）。一個被禁止再派出 agent 的 subagent，就自己直接負責 diff，並維持同樣的審查分開，這樣就算符合。不要回一句「待命中」然後去等巢狀的 agent。修改要精準下刀；從上游衍生出來的檔案，要回頭對照來源重新確認。共用基礎元件的改進，要搬到所有使用它的地方，並逐一驗證。勤快地 commit。
5. 在對應的介面上驗證。「無法判定」或驗錯了介面都不算通過。要把它標出來。
6. rebase 成小而有順序的 commit。後續的修改疊上去。
   用 **sequence-verifiable-units** 原則 skill，每個小單元都先建好、驗證、commit，再做下一個。
7. 如果設計有爭議，出貨前先跑 `interrogate`。
8. 跑 **Opening a PR**（開 PR）劇本。

程式彼此綁在一起的工作（一個功能、一次遷移）交給單一個負責人，檢查點直接寫在交代裡。那個負責人在會卡住的階段過了之後，再自己在內部分頭派工。上層的分頭派工是給那些會各自產出獨立成品的切片用的（稽核、跨子系統的調查、互相競爭的實驗）。到了階段的交界就重寫檢查點。寧可派一個新的負責人，也不要接二連三地打斷。

**回覆：** 你做了什麼、你選了什麼以及為什麼、吞吐量檢查點、還沒定的決定。設計的替代方案用表格列。
