# 不要註解

派出 Comment Sicko。處理被接受的發現。

以 Comment Sicko 不帶成見的新眼光為準。

## 範圍

用呼叫者給的檔案或 diff。沒有的話，就用目前對基準分支的 diff，基準分支預設是 `main`，也包含工作樹。

## 步驟

1. 用 `subagent_type: "comment-sicko"` 派出一個 `Task`。把範圍傳給它。依工作挑每個 subagent 的推理等級，照 **poteto-mode** skill 的 Subagents 那一節。不要重述它的規則。
2. 檢查它的報告和 diff。駁回這些：改到應用程式碼的修改、超出範圍的修改、刪掉受例外條款保護的註解、理由寫錯的 `MUST KILL`，以及把刻意留下的程式當成有罪的標記。針對我們自己程式裡出人意料之處的重塑標記，仍然是要處理的項目。不要把那些註解恢復。被留下的註解，只有在證明它講的是我們改不了的東西時，才能留著。稽核範圍內被漏掉的 lint 和 TypeScript 抑制註解。跟正確性或安全有關的抑制，仍然是要處理的 `MUST KILL`。只有在有確切的例外條款和限定範圍的證明時，才恢復被刪的東西。在接受理由單薄的 `IMPORTANT` 或 `do not remove` 註解被刪或被留之前，追查它們指的符號，或對它跑 `/why`。被刪的註解如果判斷不明確，不要恢復。被留下的註解如果被推翻或仍然不明確，就刪掉。一份被駁回的報告，把它的改動退回，點出失敗的地方，重跑一次。第二份再被駁回，就回報成未解決，並讓 `/no-comments` 判定失敗。
3. 簡單的、已接受的標記直接修：刪掉死掉的路徑、拿掉一個參數，或改用真正的 API。如果有任何修正需要先決定形狀，就針對已接受的那一批和周圍的程式跑一次 `/architect`。停在草圖。architect 決定形狀。第 4 步實作。
4. 在範圍內做最小的根本原因修正。把每一個被點名的權宜做法都移除。如果根本原因在範圍外，就落地範圍內最小的修正，其餘的回報成未解決。**principle-fix-root-causes** 和 **principle-redesign-from-first-principles** 這兩個 skill 只用來引導意圖。兩者都沒有授權你把圍欄擴大，也沒有授權你去修圍欄外的情況。絕不要外掛只擋症狀的防護。
5. 限制註解會寫 `do not remove`、`do not change wording` 或 `talk to X before changing`。講我們改不了的東西的保留註解，就留著。提議範圍內最便宜的型別、執行期、測試或 CI lint 檢查。等互動式的核准。無人看管的執行和 eval 需要呼叫者事先核准。核准了就先編成檢查，再刪掉註解。否則就刪掉，把這個限制回報成未解決，並畫出範圍外工作的草圖。
6. 回報刪除的數量、恢復的註解、重跑、architect 草圖、修正、提議的檢查、已編成的檢查、沒有強制執行的限制，以及其他未解決的工作。
