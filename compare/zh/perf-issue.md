TOPIC: 修效能問題

### 效能問題

**整套量測的來龍去脈由你負責。規劃、審查、驗證數字。** 每個修正都要綁上一次量測，不要用讀原始碼來代替量測。

1. 用對應的 control skill 錄一份基準追蹤紀錄。用 **benchmark-checklist** skill 檢查這個基準，以及之後的每個數字。
2. 追一遍程式碼，讓假設有根據。沒先實際跑過，不要宣稱效能已經到頂。
   照順序試效能口訣，最便宜的先試：
   1. 不要做。結果沒有任何地方用到的工作，直接停掉，而不是把它變便宜。
   2. 要做，但不要再做第二次。
   3. 少做一點。
   4. 晚點再做。
   5. 趁沒人在看的時候做。
   6. 同時一起做。
   7. 用更便宜的方式做。

   前面的口訣已經達到目標，就停下。
3. 根據追蹤紀錄規劃修正。如果它跨過函式邊界，先跑 `architect`。把實作委派給一個 subagent，用你設定的 perf-issue 模型（預設 `claude-opus-5-5-xhigh-fast`）。依工作挑每個 subagent 的推理等級，照 Subagents 那一節。審查 diff。錄一份修正後的追蹤紀錄。
   套用 **sequence-verifiable-units** 原則 skill，每次嘗試都驗證過，才試下一個。
4. 解析並比較這些成品（JSON 轉進 sqlite、做 diff）。「無法判定」或驗錯了介面都不算通過。要把它標出來。
5. 在 PR 裡引用量測結果。
6. 跑 **Opening a PR**（開 PR）劇本。

如果要的是朝著一個指標持續改進，而不是一次性的修正，就用 Hillclimb（逐步爬升）劇本（`playbooks/hillclimb.md`）。

**回覆：** 基準數字、修正後數字、差值、成品路徑。
