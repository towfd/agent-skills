# 技術寫作

寫到讓一個累壞的工程師第一次讀就懂。

- 刪掉每一個沒有作用的字。
- 用簡短、日常的字：說「use」（用），不要說「utilize」（利用）。
- 當一條規則讓句子變得更糟時，用別的方法修那個句子，或者別動它。
- 寫出真正的符號、檔案、旗標或指令名稱，不要用同義詞或對它的描述。
- 不要自創術語。用開發者會說出口的字。一個有名字的模式第一次出現時，說出它是什麼意思。

## 變化節奏

- 長短句混著用。帶著兩個想法的句子就拆開。只帶一個想法的長句就留著。
- 寫說明時要有觀點。寫參考時保持平淡。
- 要具體。不要寫「schema 的變更可能造成問題」，要寫「改一個欄位名稱會讓建置失敗」。

## 先選定類型（Diátaxis）

一份文件，一種類型。不要混用類型。改成拆開再互相連結。

- **教學（Tutorial）：邊做邊學。** 說出學習者會做出什麼。每一步都產生看得見的結果，而且你要說他們應該看到什麼。解釋只給一個子句加一個連結。
- **操作指南（How-to）：達成目標的步驟。** 解決讀者的問題。假設讀者有能力。只寫動作。允許分岔。用任務來替這份指南命名。
- **參考（Reference）：查閱用的事實。** 只描述。要平淡、完整、篤定。照著被描述的東西的結構來安排。
- **說明（Explanation）：理解和原因。** 一個有界線的主題。給出背景：設計決定、歷史、限制、其他選項。只有這裡可以有意見，其他地方都不行。

## 句子要對著讀者寫（Google 開發者文件風格）

- 用「你」稱呼讀者，用現在式。
- 說出誰做什麼。只有在動作者不知道是誰或無關緊要時，才可以用被動語態。
- 指示寫成命令句。條件放在指示前面，常見的情況放第一個。
- 不要用流行語、不要用比喻性的語言、不要寫「please」（請），程序裡絕不要寫「simply」「easy」或「quickly」（只要、很簡單、很快）。
- 不要事先預告，也不要讓連續的句子用同一個片語開頭。
- 連結的文字要說出連結會帶你去哪裡。
- 標題要帶出重點，用 sentence case（只有句首大寫）。每頁一個 h1，層級不要跳過。
- 有順序的用編號清單，其他一律用項目符號。用一個完整的句子帶出清單。清單項目保持平行結構。
- 程式碼用程式碼字型。UI 元素用粗體。用 serial comma（序列逗號）。不要寫「etc.」（等等）。

## 讓敘述一次載入一個（STE 規則）

- 一句一個指示。其他地方一律一句一個想法。
- 超過大約 20 個單字的指示要拆開，其他超過大約 25 個單字的句子也要拆開。
- 把警告或條件放在它所把關的那個步驟前面。
- 保留「the」和「a」（冠詞）。
- 每個字只給一個意思，每個動作只挑一個字。
- 程序寫成直接的命令，絕不寫成敘述，也絕不用被動語態。
- 能避開「-ing」字的地方就避開。

## 不要讓任何句子有兩種讀法（Global English）

- 「only」（只）和「not」（不）這類字，要緊挨著它修飾的那個字。
- 把很長的名詞串拆開。
- 讓每個「it」「they」「this」（它、它們、這）都指向一個明顯的東西。絕不要用「this」或「which」去指一整個子句。
- 不要省略動詞，也不要省略顯示結構的小字，例如「that」。
- 在一串並列裡，如果重複冠詞能避免誤讀，就重複冠詞。說清楚「and」或「or」（和、或）連接的是哪幾個部分。
- 用句號，不要用分號或 em dash。不要用斜線，也不要用「(s)」。括號裡的文字要是一個完整的文法單位。
- 每個東西在每個地方都用同一個名字。
- 不要用慣用語、口語說法、拉丁文縮寫和比喻。

## 語氣和倉庫的特定規定

- 這個 skill 碰到的每一份文件，都要套用 **unslop** skill。AI 腔的模式清單歸那個 skill 管：AI 愛用的詞、贅字、含糊的保留語氣、格式上露餡的地方。
- PR 說明和 commit 訊息也是寫作。除了 Diátaxis 以外的每一層都適用在它們身上。一份 PR 內文是一份讓審查者不到一分鐘就能讀完的簡報。不要貼 swarm 的 log、SHA 清單或指標表格。放連結。
- 產品的 UI 字串不是文件。那些要用你們產品的文案規範。
- 程式碼片段用 tab 縮排。寫真實的路徑。每一個關於數量或程式樹的說法，在把它落地的那個 commit 上都要是真的，並附上重新產生它的指令。
