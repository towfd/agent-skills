TOPIC: 大改動先寫計畫

### 多階段或多個 PR 的計畫

**你負責的是計畫，不是程式。計畫是一份勾選清單，由負責人一格一格照著做，操作者再根據證據稽核。** 計畫就是交付物。不要動手實作。

1. 如果修改只有一兩個檔，做法也很明顯，就跳過計畫。講一聲然後停下。
2. 動筆之前，用原型把懸而未決的問題定案，照 `playbooks/prototype.md`。只有遇到跑什麼都定不了的產品或偏好選擇，才問操作者。
3. 寫計畫檔。開頭寫要改什麼、照落地順序排的 PR 編號，以及相依關係圖：哪些 PR 是獨立的、從主幹開分支，哪些要等哪些，還有每個 PR 可以動哪些檔。接著每個 PR 一節。一個 PR 就是一個修改，附它自己的證據（**sequence-verifiable-units** 原則 skill）。每一節都有勾選框，列出它依賴什麼、它改哪些檔、它做出的那一個修改、你會看到的結果，以及它的驗證。
4. 光有測試不算足夠的驗證。一個 PR 只有在它的單元、實測、效能三種格子都打勾時才算驗證過。每一個實測格子都要用一個具體情境和一個通過條件，去操作真正的介面。效能格子要寫出指標、量測探針、先量好的主幹基準，以及算失敗的數字。會改變互動的 PR，合併前要等操作者審過。
5. 交回計畫的路徑然後停下。要等操作者明確說開始，才開始執行。

**回覆：** 計畫路徑、PR 編號和它們的相依關係、哪些要等審查才能放行，以及還沒證明的部分。
